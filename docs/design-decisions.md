# Design Decision Review

**Status:** Draft for team review  
**Purpose:** Capture current implementation choices, differences from the draft HLD, and proposed preferences/rationale for team discussion.  
**Note:** The preferences below are proposals for review and are not final agreed team decisions.

| ID | Design topic | What the current code does | What the HLD says | Proposed preference and rationale |
|---|---|---|---|---|
| **DD01** | JSON storage structure | Uses one `records.json` containing Client, Airline and Flight dictionaries. | Shows three files: `client.json`, `airlines.json`, `flights.json`. | **Preference: One combined file.** The assignment explicitly describes internal storage as a list of dictionaries. A single JSON array naturally serialises this structure, and the `Type` field already differentiates between record types. Persisting the collection as one JSON document maintains a direct correspondence between the in-memory structure and the persisted representation, reducing unnecessary transformation and consistency risks associated with maintaining multiple persistent files. For a production system, this decision should be reconsidered if requirements for scalability, concurrency, resilience or larger data volumes emerge, potentially requiring a different persistence mechanism such as a database. |
| **DD02** | Application components | `gui.py` calls `RecordManager`; `models.py` handles record construction/validation; `storage.py` handles JSON persistence. | Diagram shows GUI → Record Controller → Validation Service → JSON Repository. | **Preference: Keep/re-use the current modular code and update the architecture visual if needed so that it reflects the implementation.** The important point is consistency between the documented architecture and the final application. |
| **DD03** | Record field naming | Uses assignment-style names such as `"ID"`, `"Type"`, `"Name"` and `"Client_ID"`. | Uses alternatives such as `id`, `recordType`, `clientName`, `clientId`. | **Preference: Retain the field names used in the current code**, since they closely reflect the assignment specification. |
| **DD04** | Flight ID and Type | Adds `"ID"` and `"Type"` to Flight records. | Also includes Flight `id` and `recordType`, although the assignment itself does not. | **Preference: Retain `ID` and `Type` for Flight records.** A unique Flight ID enables reliable search, update and deletion of individual Flight records. The `Type` field is particularly valuable if DD01 adopts a single combined JSON file because it distinguishes Client, Airline and Flight records within the same collection. If separate JSON files were used, `Type` would be less essential because the file itself already identifies the record category. |
| **DD05** | ID allocation | Uses one global sequence across all records, e.g. Client 1, Airline 2, Flight 3. | Does not define the allocation method. | **Preference: Retain globally unique IDs.** With all record types held in one combined collection (DD01), a global ID allows each record to be uniquely identified by ID alone and simplifies CRUD operations. For a larger production system, the identification strategy should be reconsidered as part of the wider data and persistence architecture. |
| **DD06** | Flight references | `Client_ID` and `Airline_ID` are integers and must reference existing records of the correct type. | Marks them as foreign keys but gives their data type as string. | **Preference: Retain integers**, which is consistent with the assignment specification and the integer IDs used for Client and Airline records. |
| **DD07** | Referential integrity | A Flight cannot be created with an unknown Client/Airline, and a Client/Airline cannot be deleted while a Flight references it. | Shows the relationships in the ERD but does not define the behaviour in detail. | **Preference: Retain the current code behaviour.** A Flight must reference an existing Client and Airline, and referenced Client/Airline records should not be deleted while dependent Flight records exist. This prevents orphaned Flight records. No further ERD complexity is required for the assignment. |
| **DD08** | Validation rules | Requires Client Name and Airline Company Name; requires Flight IDs/date/start/end; validates IDs as integers; trims whitespace and standardises Flight date input. | Validation detail is largely to be completed. | **Preference: Retain the current validation and normalisation.** It already enforces required fields, trims whitespace, validates integer references and standardises Flight date input. More advanced controls such as duplicate-client detection, country reference lists, phone-number validation and address verification can be identified as possible production enhancements rather than assignment requirements. |
| **DD09** | Flight date format | Stores text such as `2026-09-15 10:30`. | JSON example uses `2026-09-15T10:30:00Z`. | **Preference: Retain the current format for simplicity.** A real-world travel application would need explicit timezone handling, but adding UTC/timezone semantics here would also require decisions around local time, conversion and daylight-saving behaviour that are outside the current scope. |
| **DD10** | Search behaviour | Searches within the selected record type using a case-insensitive substring match across fields. | Does not define detailed search behaviour. | **Preference: Retain the current search behaviour.** It provides flexible search functionality while remaining simple and aligned with the assignment. |
| **DD11** | Persistence timing | CRUD operations modify the in-memory list; the complete list is saved to JSON when the GUI closes and loaded at startup. | FR5/FR6 say load at startup and save on closure; the state diagram may imply records are stored earlier. | **Preference: Team decision required.** Option 1 is to retain the current save-on-closure approach and explicitly document the risk of data loss if the application exits unexpectedly. Option 2 is to enhance the application so that each successful create/update/delete also persists the JSON file. Either approach can be justified if the trade-off is documented clearly. |
| **DD12** | Load/Save interaction | Load and save are automatic system behaviours; the user does not manually trigger them. | Use cases show Load and Save associated with the Travel Agent, while FR5/FR6 describe automatic startup/closure behaviour. | **Preference: Retain the current automatic behaviour.** The intent of the implementation and functional requirements is aligned; the HLD use-case representation can be clarified if required. |
| **DD13** | Error handling / logging | Validation errors are converted into user-friendly GUI messages; there is no logging facility. | NFR states that exceptions are logged and user-friendly messages are displayed. | **Preference: Add lightweight logging to the existing code.** Use Python's `logging` module for unexpected errors and persistence failures while retaining user-friendly GUI messages. |
| **DD14** | Performance requirement | No explicit performance measurement is implemented. | States that common operations should complete in under one second. | **Preference: Add performance testing.** Measure the key operations required by the assignment—Create, Delete, Update and Search/Display—against a representative dataset. Use automated timing (for example `time.perf_counter()`) and repeated runs so the performance claim is supported by evidence rather than assumed. |

## Suggested next step

Review each decision as a team and update this file with the agreed outcome. Once decisions are confirmed, we can align for implementation, tests and final report with the agreed design.
